## 一句话介绍

一个基于**麦当劳中国官方 MCP** 的点餐助手。它的起点不是菜单，是**你的历史订单**——
交互动词是「改」，不是「选」。

## 它解决什么问题

麦当劳 App 只会向你**推销**，不会替你**记住**。

真实的老客行为不是「每次重新做一遍选择题」，而是：

- 一周五个工作日，早餐基本就那两三样；
- 午餐在固定两三家门店、固定几个套餐之间轮换；
- 变化往往只有一处 —— 「今天不要薯饼」「饮料换无糖」「预算压到 25 以内」。

| | 麦当劳 App | 麦麦老样子 |
| --- | --- | --- |
| 起点 | 全量菜单 + 推荐位 | **你最近一单** |
| 交互 | 重新挑选 | **说一句「改哪里」** |
| 金额 | 平台标价 | **每次 MCP 官方核价**，界面可查 `traceId` |
| 下单 | 直接支付 | **必须勾选「我已核对」才发请求** |

**目标用户**：一周吃三次以上麦当劳、有自己的固定搭配、懒得每次重新翻菜单的人。

## 快速开始

### 1. 申请 MCP Token

打开 <https://open.mcd.cn/mcp> → 手机号登录 → 右上角「控制台」→「激活」→ 同意协议 → 复制 Token。

### 2. 运行

```bash
git clone https://github.com/EAnge1o/mcd-repeat-smarter.git
cd mcd-repeat-smarter && npm install

cp .env.example .env      # 填入 MCD_MCP_TOKEN=你的Token
npm run build && npm start
```

打开 <http://127.0.0.1:8787>。

开发模式用 `npm run dev`（前端 5173 + 服务端 8787）。**不要同时开着 dev 和 start**——两者都监听 8787。

### 3. 不想配 Token？

```bash
DEMO_MODE=true npm run dev
```

内置演示数据跑通完整流程，界面上有强制警示条，所有金额标记为演示，下单接口只返回模拟结果。

### 4. 自检连接

```bash
npm run mcp:probe    # 只读，列出 MCP 全部 Tool、门店在售数、可读订单数、一次真实核价
```

## 使用示例

真机跑过的输入（门店 `1450713`，到店自取）。

**`还是上次那份，不过今天不要香芋派，换个东西，预算不超过 16 元`**

1. 从 `order-list` 取最近一单：`随心配1+1`（那么大鸡排 + 香芋派）；
2. 发现 `随心配1+1`（`9900010829`）**已不在当前门店在售菜单里**；
3. 按核心词重匹配到在售的 `人气经典随心配`，并**明确提示「编码已更新 → 现已对应「人气经典随心配」」**；
4. 在粉区把香芋派换成另一种派/小食，给出 2 个候选；
5. 每个候选各调一次 `calculate-price`，官方核价 **¥13.90**，在 ¥16 预算内。

**其他几种说法**：`还是老样子`（原样重复，只核价）· `加一份麦乐鸡`（增一件，其余不动）· 调好后存成常用方案（**存结构化餐品编码与规格，不存那句话，也不存价格**——价格有时效，下次用必重新核价）。

## 它是怎么工作的

```
浏览器 (React 19 + TS + Vite)
   │  只发业务请求，永远拿不到 Token
   ▼
Express (Node)  ← MCD_MCP_TOKEN 只在这里
   ├── server/mcp/      手写 MCP Streamable HTTP 客户端（JSON-RPC 2.0）
   ├── server/domain/    纯函数领域逻辑：意图 / 匹配 / 规划 / 定价
   ├── server/store/     常用方案持久化（原子写）
   └── server/routes/    对外 API + 下单安全闸门
   ▼
https://mcp.mcd.cn  (麦当劳官方 MCP Server)
```

一次「调整」的完整链路：

```
POST /api/adjust
 ├─ 规则引擎 → ParsedIntent          （不要X / 换个东西 / 不超过N）
 ├─ query-meals       → 门店当前在售清单
 ├─ query-meal-detail → 套餐轮次结构
 ├─ matchPlan()       → 商品身份重匹配（含别名、换码、下架）
 ├─ buildCandidates() → 2~3 个候选
 ├─ calculate-price×N → 逐候选官方核价
 ├─ verifyBreakdown() → 覆盖性/合计一致性/零金额 三类自检
 └─ markBudget()      → 预算判定 + 超预算说明
```

**为什么不用 MCP SDK**：只用到 `initialize` / `tools/list` / `tools/call` 三个方法，手写 226 行即可，也更容易看清「Token 具体在哪一行被使用」。

**领域层是纯函数**：不碰网络、不碰文件，因此 79 个测试里有 57 个能用固定 fixture 直接跑。

## 关键设计决策

**1. 金额一律用「分」的整数存储。**
`calculate-price` 返回「分」，`query-meals` 的 `currentPrice` 是「元」的字符串，混用会差 100 倍。

**2. 商品身份与展示信息分离，并且承认「身份会漂移」。**
用户最爱的 `随心配1+1` 已下架。直接报错是偷懒，静默换成别的是欺骗。做法是按核心词重匹配到在售商品 + **显式告知「编码已更新」**，并保留 `aliasNames` 让用户之后仍能用旧名字提修改。

**3. 价格只来自 MCP，模型不参与算钱。**
每个金额都对应一次真实 `calculate-price`，界面能看到 `traceId`。演示模式的金额带 `source: 'demo'`，绝不冒充。

**4. 下单是两段式的，绕过 UI 也拿不到 200。**
`/order/preview` 再核一次价并签发 **5 分钟有效、绑定门店/商品/金额/取餐方式的一次性令牌**；`/order/confirm` 必须带 `confirmed: true` 和这个令牌，否则 428 / 410。UI 上按钮在勾选前是 disabled 的，但真正的闸门在服务端——测试里有一个专门用例断言**未确认时 `createOrder` 的调用次数恰好为 0**。

**5. 意图解析用规则引擎，不用 LLM。**
「不要 X，换个东西，不超过 25」这类句式高度集中，正则 + 中文数字解析就够，结果稳定可测。代价是能理解的句式有限——这是明确取舍，见[已知限制](#已知限制)。

**6. 不理解的地方不猜。**
识别不了的片段会进 `unrecognized`，界面提示「有一部分没听懂」并给出可用说法示例，而不是假装懂了乱改。

## 界面

**点单**：说一句话 → 右边给出「原方案 → 调整后」的前后对照和候选方案，每个金额带官方 `traceId`。候选选中态用黑底反白——因为卡里同时有白字正文、金色金额和黄底徽章三种对比，黑底是唯一能同时容纳三者的底色。

![点单结果](docs/screenshots/order-desktop.png)

**确认**：门店、餐品（含套餐里具体选了什么）、改动、取餐方式、金额全列出，**必须勾选「我已核对」下单按钮才激活**。

![确认下单](docs/screenshots/confirm-checked.png)

**订单记录 / 常用方案**：

![订单记录](docs/screenshots/orders-desktop.png)

**字体**：标题与**全部数字**都用**融合像素字体**（Fusion Pixel Font，OFL-1.1）。麦当劳的视觉血缘是 8-bit 游戏机与街机柜台——有限色、硬边、点阵字形，所以标题不用超粗黑体而用点阵字；金额、计数、时间戳、订单号也一并点阵化，因为 8-bit 柜台机的收银小票就是这个质感，而一个 `¥129.04` 用点阵排出来比用黑体更像「机器算出来的、真的花了这么多」。

实现上不是给每个数字包 span，而是让 `.tnum` 这个「数字专用类」自带点阵字体——一处改动覆盖全站 40+ 处数字，新增数字自动生效。数字走点阵、同元素里的中文自动落到黑体，「共 10 单」这种混排不需要拆 JSX。字体按 Unicode 分片只下发实际用到的 **25 片（554 KB）**，正文中文仍是黑体。**署名见 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)。**

## 它不是什么

- **不是推荐引擎** —— 它不做「今天吃什么」，只处理「上次那份，改一处」。
- **不是省钱的** —— 预算只是约束，不是目标。预算不满足时给最接近的方案并说明原因，**不会偷偷换掉你要的东西**。
- **不代替你下单** —— 勾选确认这一步不能省，这是把「改一句话」和「花一笔钱」之间那道闸门。

## 已知限制

| 限制 | 原因 | 影响 |
| --- | --- | --- |
| 只支持到店自取 | UI 只开放 `beType=1`；外送/得来速需地址与时段 | 外送用户用不了 |
| 历史订单不返回轮次与图片 | MCP `order-list` 字段所限 | 子项轮次靠按名称反查套餐结构推断，同名商品跨轮次时可能推错，此时标记为需确认 |
| 不会还原上次的特制项 | 历史订单不返回少冰/去酱 | 「老样子」还原的是餐品结构，不含特制偏好 |
| 意图解析句式有限 | 规则引擎，不是 LLM | 复杂说法会被标记为「没听懂」，而不是瞎猜 |
| 不做反向求解 | 只执行用户明确说的改动 | 不主动优化搭配 |
| 单笔只能用 1 张券 | 官方规则 | 不做多券叠加，不代选券 |
| 常用方案是单机文件存储 | 无账号体系 | 换设备/换浏览器拿不到 |
| 演示数据是内置的 | 无 Token 时的体验模式 | 只用于演示流程，不代表真实供应 |
