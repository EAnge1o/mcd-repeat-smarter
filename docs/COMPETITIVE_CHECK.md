## 5. 本项目的差异点（三条，都可被验证）

1. **以"我的历史"为起点，而不是以"全量菜单"为起点。**
   原方案来自真实 `order-list`（或用户保存的方案），用户只需说明"哪里要改"。省掉的不是钱，是每次重新翻菜单的决策成本。

2. **"增量修改"是一等公民，而不是筛选条件。**
   `保留 / 删除 / 替换 / 新增 / 预算 / 偏好` 被建模成结构化变更，并且**每一处变更都要在界面上说清楚**（"改了什么"两列对比 + 变更标签）。同类项目基本都是"给一批推荐让你挑"，没有"只动你指定的那一个"。

3. **商品身份漂移被显式处理。**
   历史订单里的 `9900010829 随心配1+1` 现在已不在售，系统会按核心词重匹配到在售的 `人气经典随心配`，并**弹出黄色提示让用户确认**，而不是静默换成别的东西，也不是直接报错。这一点是在真实账号数据上撞出来的，也是历史订单类功能最容易翻车的地方。

补充一句范围控制：本项目**没有**做积分抵扣、多券叠加、多人分账、营养分析。这些方向要么已被做透，要么会显著拉长主流程，与"一句话改一单"的核心体验冲突。
